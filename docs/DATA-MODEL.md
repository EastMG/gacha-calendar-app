# 数据模型

## 为什么要派生

上游 core 的 `Result JSON`（`schemaVersion: 1`）是**为桌面表格排版设计的**：
每个字段都是"给人看的字符串"，没有一个是可计算的时间戳。

```jsonc
{
  "schemaVersion": 1,
  "refreshedAt": 1792535087132,
  "parserVersions": { "genshin": 1, "zzz": 2, "nte": 3 },
  "games": {
    "genshin": {
      "name": "原神",
      "banner": "「虚星临渡」107期角色活动祈愿",
      "roles": "「虚渊暗星·丝克克(冰)」、「明绚千韵·爱可菲(冰)」",
      "bannerDates": "10-13 18:00 ~ 11-03 14:59",      // ← 没有年份
      "bannerDatesRaw": "10-13 18:00 ~ 11-03 14:59",   // ← 源站原文，各站写法不同
      "bannerHover": "「虚星临渡」107期角色活动祈愿：「虚渊暗星·丝克克(冰)」\n「莓色香颂」107-2期…\n10-13 18:00 ~ 11-03 14:59",
      "event": "「往冥府的安魂歌」",
      "eventDates": "09-23 10:00 ~ 11-03 14:59",
      "eventHover": "「虹旅藏金·耀星烁熠」   09-28 00:00 ~ 10-22 06:00\n「判测胜券本征」   10-12 10:00 ~ 10-23 09:59\n…",
      "gachaFail": null,
      "eventFail": null,
      "gachaStale": false,
      "eventStale": false,
      "okAt": 1792535087132
    }
  }
}
```

倒计时、日历、提醒都需要**绝对时刻**，因此有了 `packages/schedule` 这一层。

## `ScheduleEvent`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 稳定 id，`gameId:kind:startAt`（明细加 `d:` 前缀）。用于列表 key 与"已提醒"标记 |
| `gameId` / `gameName` | `string` | 游戏标识与显示名 |
| `kind` | `"gacha" \| "event"` | 卡池 / 活动 |
| `kindLabel` | `string` | 「卡池」/「活动」 |
| `title` | `string` | 卡池名或活动名 |
| `detail` | `string` | 角色名等附加信息（来自 `roles`） |
| `startAt` / `endAt` | `number` | **绝对毫秒** |
| `precision` | `"minute" \| "day"` | 见下 |
| `tzMin` | `number` | 该事件按**哪个时区**记录（分钟偏移） |
| `origin` | `"primary" \| "detail"` | 当期主事件 / 从 `*Hover` 明细展开的额外事件 |
| `fail` | `FailInfo \| null` | core 的三态失败语义 |
| `stale` | `boolean` | 该列沿用上次缓存 |
| `rawDates` | `string` | 源站原始文本，排错用 |

### `precision` 的意义

- `"minute"`：源站给了时分，可以倒计时到分钟、可以排提醒。
- `"day"`：源站**只给了日期**。此时：

  - 界面只显示"剩 3 天"，**绝不显示"剩 3 小时 12 分"**；
  - `planReminders()` **不为它排提醒** —— 不知道确切时刻，排"提前 1 小时"等于编造。

实测 28 款里，`gf2` 的活动原始串 `2026年10月13日 版本更新后~2026年11月3日 08:59`
起始侧没有时分，因此被正确地降级为 `day`。

## 时区

**这是移动端最隐蔽的坑。** 这里刻意不使用 `Intl`/IANA 时区名，只用整数偏移，
原因见 [`../packages/schedule/src/timezone.ts`](../packages/schedule/src/timezone.ts) 顶部。

三条结论支撑这个选择：

1. 28 款游戏只用到 **3 个时区**；
2. 三者**全部是固定偏移、无夏令时**（国服 `+480`、日服 `+540`、国际服/UTC `0`）；
3. 因此纯整数运算与 `Intl` 逐毫秒等价。

## 年份推断

展示串没有年份，必须推断。算法：在 `now` 的前后一年共三个候选里，
取**离现在最近**的那个（`parse-window.ts` 的 `inferYear`）。

跨年区间（`12-28 ~ 01-05`）另外处理：若结束早于开始，把结束推到下一年。

### 已知局限

`*Hover` 明细里可能含**归档的历史活动**，它们的区间同样没有年份，
推断时可能被映射到"今年"从而显示成"进行中"。

当前策略：
- 只对主事件做完整展示；
- 明细事件保留 `origin: "detail"` 标记，界面上可区分；
- 后续应对明细加"合理性窗口"（例如只在 `now ± 45 天` 内展示），或
  让上游在明细里带上年份。**这是上线前要解决的一项。**

## 观测到的日期格式

用 2026-10-20 的真实快照统计（43 个有日期的侧）：

| 形态 | 出现次数 | 例子 |
|---|---|---|
| `MM-DD HH:mm ~ MM-DD HH:mm`（无年份） | 42 | `10-13 18:00 ~ 11-03 14:59` |
| `YYYY-MM-DD HH:mm ~ YYYY-MM-DD HH:mm` | 1 | `2026-10-19 12:00 ~ 2027-01-25 04:59`（gf2 活动） |
| 空（无当期数据） | 13 | — |

`*DatesRaw` 里还有更多写法，解析器额外支持：

- 全角分隔符：`10/13 12:00 ～ 10/26 11:59`
- 中文日期 + 版本用语：`2026年10月13日 版本更新后~2026年11月3日 08:59`
- 只有日期：`10-13 ~ 11-03`（→ `day` 精度）

## 实测数字（2026-10-20 快照）

| 指标 | 数值 |
|---|---|
| 游戏数 | 28 |
| 有日期的侧 | 43 / 56 |
| 主事件 | 43 |
| 明细展开事件 | 96–102（随当期数据而变） |

## 两个上游契约缺口

1. **`listGames()` 不返回 `tz`**：见上。
2. **`Result JSON` 无法表达"该侧未配置来源"**：那种情况会被算成成功，
   只有 `selfCheck()` 的 `unconfigured` 才知道。
   `toGameViews()` 因此把"既没有失败、也没有任何内容"归一成 `empty`（界面显示"无数据"），
   既不冒充成功，也不误报失败。

## 其他观测

- **`*Hover` 里存在完全重复的行**（实测原神「绮星盛会」同一区间连写两遍）。
  `toEvents()` 按 id 去重，否则界面会出现重复卡片。
- core 的一轮刷新只抓**可见条目**（`hidden` 之外的）。
  这既是性能优化，也意味着"隐藏的游戏不会更新"。
